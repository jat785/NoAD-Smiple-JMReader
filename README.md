# JMReader

禁漫天堂（JMComic / 18comic）第三方阅读器。**只做漫画**，没有广告、没有小说、没有视频。

前后端分离：后端 FastAPI + SQLite，前端零依赖的静态页面（无框架、无构建步骤）。

## 特性

| 功能 | 说明 |
|---|---|
| **默认页随机** | 打开就是随机 10 部漫画，点「换一批」重掷；池子约 550 部，不是固定那几部 |
| **JM 号定位（车牌号）** | 搜索框里直接输数字就是车牌号，精确定位到那一部，命中即出卡片 |
| **关键词搜索** | 站内 / 作品 / 作者 / 人物，支持排序（最新·观看·图片·爱心·评分·评论）与时间范围 |
| **标签搜索** | 走禁漫原生的 `main_tag=3`，不是拿标签当关键词凑 |
| **标签筛选（多选）** | 内置标签点一下就选中，可多选；支持「同时具备」与「任一即可」两种模式 |
| **分类与排行** | 分类树、标签云、日/周/月/总排行 |
| **收藏夹** | 登录后读取你自己的禁漫收藏夹（含收藏夹分组） |
| **登录状态自动维护** | 禁漫登录态只有几小时；可选「记住密码」，失效后自动重登且**从不保存明文密码** |
| **观看历史** | 存在本地，记录到**章节 + 页码**，可以「继续阅读」 |
| **在线阅读** | 长图（下拉）/ 翻页两种模式，阅读进度自动记录 |
| **下载到本地** | 一章一个 ZIP，零重编码零画质损失；可浏览、可阅读、可删除 |
| **本地库** | 「本地」页浏览已下载的漫画，直接读 ZIP 里的图 |
| **排版照搬禁漫网页端** | 宽屏是竖版封面多列网格，封面叠作者/分类徽章，下方标题 + 橙色作者 + 灰色信息行；窄屏自动切列表 |
| **深浅色主题** | 跟随系统 / 深色 / 浅色，随手切换 |
| **无广告** | 用的是禁漫的移动端接口，从头到尾不请求任何广告字段 |

## 快速开始

> 需要 **Python 3.10 或更高版本**（推荐 3.12+）。

依赖**全部装在项目目录内的 `.venv` 里**，不会污染你的全局 Python 环境。

### Windows

```bat
git clone <你的仓库地址> JMReader
cd JMReader
run.bat
```

> ⚠️ **请用 `git clone`，不要用拷贝 / 解压的方式获取本项目。**
>
> `.bat` 必须是 **CRLF** 行尾。这条转换由 git 在检出时完成 ——
> **拷贝、解压、或者用 robocopy 搬过去的文件，git 完全不知情，落到盘上的行尾就保持原样。**
>
> 而一个「带中文 + LF 行尾」的 `.bat` 会让 cmd 的解析器错乱：双击后窗口
> **一闪就退，什么都不显示**。这不是推测，是真的踩过 ——
> 当时报的是一串 `'import' is not recognized`、`WinError 123` 循环。
>
> 现在的 `run.bat` 已经做成**全 ASCII + 出错必定 pause**，即使行尾不对也不会
> 静默失败（实测把纯 LF 版本跑起来，能正常走到报错并停下等你按键）。
> 但用 clone 仍然是唯一正确的做法。

### macOS / Linux

```bash
git clone <你的仓库地址> JMReader
cd JMReader
./run.sh
```

> `run.sh` 的可执行位已经存进 git，正常不需要 `chmod`。若因为文件系统（如
> 某些挂载参数）丢了权限位，`chmod +x run.sh` 一下即可。
>
> ⚠️ `run.sh` 目前**未在真实 macOS / Linux 上实测**（本项目的开发和验证环境是
> Windows）。换行符已由 `.gitattributes` 固定为 LF，静态检查也没有发现问题，
> 但如果你跑出问题，请提 issue。

看到下面这行就说明起来了，浏览器打开即可：

```
JMReader 正在启动 …
本机打开： http://127.0.0.1:8756
```

如果你把 `JMREADER_HOST` 改成了 `0.0.0.0`（想让局域网访问），这里会改成列出本机可用的局域网地址 —— 因为 `0.0.0.0` 本身是个"监听所有网卡"的通配地址，**不能拿它当网址打开**。

### 手动安装（等价于上面的脚本）

```bash
# 1. 在项目目录内创建虚拟环境
python  -m venv .venv      # Windows
python3 -m venv .venv      # macOS / Linux（这两台上通常没有 python 这个名字）

# 2. 不要激活，直接用 venv 里的解释器装依赖
.venv\Scripts\python.exe -m pip install -r requirements.txt   # Windows
./.venv/bin/python       -m pip install -r requirements.txt   # macOS / Linux

# 3. 启动（同样用 venv 里的解释器）
.venv\Scripts\python.exe -m app        # Windows
./.venv/bin/python       -m app        # macOS / Linux
```

> Debian / Ubuntu 上如果 `python3 -m venv` 报错说缺少 venv 模块，先装它：
> `sudo apt install python3-venv`。

> ⚠️ 请不要用 `pip install --user` 或全局 `pip install`。这个项目所有依赖都应当只存在于 `.venv/`。
>
> ⚠️ **不要依赖 `activate` 脚本来切换环境**，下面这种写法在 PowerShell 里会静默失效：
>
> ```powershell
> .venv\Scripts\activate        # ← 在 PowerShell 里这样写没有效果
> pip install -r requirements.txt
> ```
>
> PowerShell 默认的 `PATHEXT` 不含 `.ps1`，所以这行会去执行 `activate.bat`，而批处理是在**子进程**里跑的，它改的 `PATH` 留不在当前会话。结果 `pip install` 落到**全局 pip**、`python -m app` 用上**全局 python** —— 正好是这个项目最不希望你做的事。
>
> 一定要激活的话，PowerShell 里用 `.venv\Scripts\Activate.ps1`（可能需要先 `Set-ExecutionPolicy -Scope Process RemoteSigned`）。但上面那种"直接用 venv 里的解释器"的写法更省心，也不依赖 shell 类型。

## 登录与凭据安全

### 先讲清楚：禁漫的登录状态只有几小时

实测数据（同一个账号，期间**没有**在别处登录过）：

| 距登录 | 结果 |
|---|---|
| 1.8 小时 | ✅ 收藏夹正常返回 |
| 3.7 小时 | ❌ `{"code":401,"errorMsg":"請先登入會員"}` |

所以失效发生在 **1.8 ~ 3.7 小时之间**，是服务端的时间限制，客户端无法延长。
顺带一提，这不是网站"不会发长寿命 Cookie"——同一个站点匿名请求的响应头里
`theme` 有效期 **180 天**、`__cflb` **24 小时**，**唯独登录令牌是短命的**。

登录令牌（`AVS`）是个不透明的随机串，**不含过期时间**，客户端无法预知它何时失效，
只能等某次请求真的被拒。

### 「记住密码」是怎么做的

本程序**从不保存明文密码**。勾选「记住密码」后，凭据按下面的顺序挑**第一个可用**的
机制密封保存，强度从高到低：

**1. Windows：DPAPI（`CryptProtectData`）—— 已在 Windows 实测**

- 密钥由 Windows 从**当前用户账户**派生，**不存放在任何文件里**
- 密文绑定「这台机器 + 这个 Windows 用户」
- 因此：数据库被拷到别的机器 → **解不开**；同机其它 Windows 用户读到 → **解不开**
- 通过 `ctypes` 直接调系统 API，**不引入任何新依赖**

**2. macOS：登录钥匙串（`security` 命令）—— 未实测**

- 密码交给**系统钥匙串**保存，由 macOS 按你的账户保护
- **密码根本不写进 `jmreader.db`** —— 库里只有一个标记，拷走数据库也拿不到密码
- 用的是系统自带命令，不需要装任何东西

**3. Linux：Secret Service（`secret-tool`）—— 未实测**

- 密码交给系统密钥环（GNOME Keyring / KWallet 等），同样是**密码不进数据库**
- 需要系统装了 `libsecret` 且钥匙串守护进程在运行；没有就自动降级到第 4 种

**4. 兜底：AES-256-GCM + 机器绑定的本地密钥**

前三种都不可用时（例如精简的 Linux 容器）才走这条。密钥文件在 `data/secret.key`
（尽力设成 0600），但用它之前还要**再混入本机身份**（主机名 + 用户名 + home 路径）
做一次 PBKDF2。所以：

- 单独把 `jmreader.db` 交出去 → 解不开
- **把整个 `data/` 目录拷到另一台机器 → 同样解不开**（光有密钥文件不够）

它仍然不是操作系统级的保护，属于**混淆级别**；拿到这台机器上同一用户权限的人
依旧能解密。界面上会如实标出当前用的是哪一种、以及它是否安全。

> 主机名会变的场景（比如容器每次重建都换 hostname）可以用环境变量
> `JMREADER_SECRET_BIND` 固定一个字符串，否则每次重建都要重新登录一次。

### 会话过期之后

- 本程序会**用存下的凭据自动重新登录一次**，然后把原请求重试一遍
- **失败绝不会连环重试** —— 密码改过时反复重试看起来就是撞库，可能触发风控甚至锁号。
  所以设计为：单次尝试 → 失败退避（30s / 5min / 30min）→ 连续失败 3 次就彻底停手，
  转为提示你手动登录
- 「退出登录」会**连同保存的密码一起删掉**，不是留着不管

### 改了代码一定要重启（否则你会看到一堆假故障）

**Python 把模块加载进内存后，改磁盘上的文件对已运行的进程没有任何影响。**
这不是本项目的特性，是 Python 本身的行为 —— 但它造成的症状非常误导人：

- 新加的接口返回 **405 Method Not Allowed**（旧进程里根本没这个路由）
- 新加的字段拿不到，界面把"信息缺失"显示成别的意思
- 界面文案、行为都还是老的

如果你只在本地改了代码、或者把新代码拷到了 NAS 却没重启服务，就会撞上这些。
**先把程序彻底关掉再启动一次**，绝大多数"莫名其妙"会直接消失。

更麻烦的是：**光看现象分不清"代码旧"和"缓存旧"**（我就在这里判断错过一次）。
所以现在 `/api/health` 和 `/api/account` 都会返回一个按源码内容算的指纹：

```json
"build": { "running": "762ee013f6e8", "on_disk": "59485cdd5ff5", "stale": true }
```

- `running` —— 进程启动时加载的那份代码
- `on_disk` —— 此刻磁盘上的代码
- `stale` —— 两者不同，即"新代码已就位，但进程还跑着旧的"

`stale` 为真时，设置页顶部会直接显示一条提示，说明需要重启。

### 前端静态资源的缓存策略

`/api/*` 一律 `no-store`（实时数据，绝不能被复用）。
`html / js / css` 用 `no-cache, must-revalidate`：**允许缓存，但每次必须回源校验**，
配合 ETag 命中时返回 304，只传几十字节。

这里特意没用 `no-store` —— 那会让浏览器每次重下整个 `app.js`（现在 60KB+）。
`no-cache` 这个名字有歧义，它不是"不缓存"，而是"不直接用缓存，先问一下"。

### 明文凭据排查

项目里不存在明文密码或明文账号：

- **仓库**：源码、脚本、`.env.example` 里没有任何真实账号密码（`.env` 本身被 gitignore）
- **数据库**：`kv.session`（含用户名与 Cookie）和 `kv.credentials`（含密码）都是密封令牌，
  形如 `v1:dpapi:AQAAANCMnd8BF...`，**直接看数据库看不到任何明文**
- **日志**：密码不进任何日志；接口响应里也从不返回密码
- **旧版本升级**：早期版本存的是明文 JSON，读取时会**自动就地重新加密**

> 顺带说明：DPAPI 的密文是**机器 + 用户绑定**的。所以数据库从一台机器拷到另一台后，
> 里面存的密码**在新机器上解不开**，程序会按「未登录」处理并要求你重新登录。
> 这是正确行为，不是 bug。

## 几个设计决定（以及为什么）

**为什么后端用 Python？**
整套生态都在 Python：[jmcomic](https://github.com/hect0x7/JMComic-Crawler-Python)（MIT，7k+ star）
已经处理好了最麻烦的部分 —— 移动端接口的加解密、**Cloudflare 绕过、域名失效自动切换与重试**。
实测启动时它会自己从域名服务器拉到最新域名，并把 `APP_VERSION` 从 2.1.7 自动升到 2.1.8。
这些才是这类项目真正的死因，而不是"少个接口"。

**为什么图片必须由后端代理？**
实测图床域名的 **TLS 证书校验会失败**，而且域名在轮换（`cdn-msp*.jmapiproxy*.cc` /
`*.jmapinodeudzn.net`），还会挑 Referer。浏览器直连必然挂。
所以封面和章节图全部走 `/api/cover/*` 和 `/api/page/*`，由后端解扰 + 转发 + 本地缓存。

**为什么下载用 ZIP？**
- **零重编码、零画质损失**：图片原样装进 ZIP（`ZIP_STORED`）。实测 13 张图共 2,886,798 字节，
  ZIP 内 `compressed == original`，容器开销只有几百字节。
- **随机访问最快**：读第 37 页只解压那一页。
- **反面对照**：同样的 webp 转成 PDF 会膨胀到 **4～10 倍**（PDF 标准不支持 webp，
  `img2pdf` 只能解码成裸像素再用 zlib 压回去；换成 JPEG 则是有损）。
- **长图不适合当存储格式**：一张超长图的解码内存峰值可达上百 MB，
  而且浏览器对单图尺寸有上限（约 16384px）。所以"长图"我们做成**前端阅读模式**
  （把多页放在一条垂直流里上下排列），观感一样，零 CPU 零重编码。

**为什么只有 1 个下载任务？**
禁漫站点运营不易。这个项目在下载上刻意保持克制：同时只跑一个任务、页与页之间留间隔、
失败才退避重试。**请不要为了"快"去调大 `JMREADER_DOWNLOAD_CONCURRENCY`** ——
真的没必要，也不体面。

**代理怎么配（这是最容易卡住的一步）**

直接连禁漫是**不稳定**的：本机实测连续 5 次只有 2 次能通，其余是
`CertificateVerifyError`（证书校验不过）或连接被重置。挂上本地代理后每次都稳定。

所以推荐挂代理，但**不需要改文件** —— 打开 App 的「设置」页面 →「网络代理」：

| 模式 | 含义 |
|---|---|
| 跟随系统 / 配置文件 | 默认。优先用 `JMREADER_PROXY`，没设就让 jmcomic 探测系统代理 |
| 不使用代理（直连） | 强制直连，连系统代理都不看。一般只用来排查问题 |
| 手动指定代理 | 填 `http://127.0.0.1:7890` 这类地址，比如 Clash / v2rayN |

页面里还有「测试连接」，会真的连一次禁漫并回报成功/失败、耗时、以及失败原因。
设置存在本地数据库里，**优先级高于 `.env`**，所以每台机器都能自己配。

常见端口：Clash `7890`、v2rayN `10809`、Fiddler `8888`。
另外 jmcomic 还认识 `clash` / `v2ray` / `fiddler` / `system` 这几个简写。

**为什么"跟随系统"在 NAS 上曾经失效（踩坑记录）**

jmcomic 有两个坑叠在一起，值得写下来免得后人重踩：

1. `JmModuleConfig.DEFAULT_PROXIES = ProxyBuilder.system_proxy()` 是**类属性**，
   在模块 import 那一刻就算死了。如果进程启动的瞬间探测不到代理
   （NAS 上很常见：以服务方式运行、Clash 还没起来、注册表读不到），
   它就**永远是 `{}`**，之后用户再怎么开代理都没用，除非重启进程。

2. 更隐蔽的是 `JmOption.merge_default_dict` 做的是**递归深合并**：

   ```python
   for key, value in user_dict.items():
       if isinstance(value, dict) and isinstance(default_dict.get(key), dict):
           default_dict[key] = merge_default_dict(value, default_dict[key])
   ```

   传 `proxies={}` 进去时，循环体一次都不执行，于是**原样返回默认值**。
   也就是说：**空字典在 option 配置里根本无法表达"不使用代理"**，
   它会被系统代理悄悄顶掉。

   这个坑极难发现 —— 我们本机测试时"直连"模式显示的确实是 `{}`，
   但那只是因为当时系统代理恰好关着、默认值本来就是 `{}`，**纯属巧合掩盖了 bug**。

所以本项目**不走 option 配置传代理**，而是在 `new_jm_client(proxies=...)` 时下发
（那条路是 `meta_data.update(kwargs)`，不经过合并）。这样三种模式都准确，
且每次构建 option 都重新探测系统代理，不再吃 import 时刻的冻结值。

`GET /api/settings` 里的 `diagnostics` 会直接给出 `injected`（实际到达 HTTP 层的值）
和 `jmcomic_default_at_import`（那个冻结值），方便对比排查。

**让别的机器访问（注意：这跟代理是两码事）**

很多人会把这两个地址搞混，结果填了 `0.0.0.0:7890` 当代理，怎么也连不上。

| | 是什么 | 填什么 |
|---|---|---|
| `JMREADER_HOST` | 本程序**监听**在哪个网卡 | 想让别的机器访问就填 `0.0.0.0` |
| 设置页的代理 | 本程序**连出去**时走哪个代理 | JMReader 和 Clash 同机就填 `127.0.0.1:7890` |

`0.0.0.0` 的含义是"监听所有网卡"，**它不是一个能连过去的地址**，
所以只能填在 `JMREADER_HOST` 里，不能填到代理框。

改完 `JMREADER_HOST=0.0.0.0` 重启后，在别的机器浏览器里打开
`http://<这台机器的局域网IP>:8756`。设置页的「访问地址」卡片会直接把可用的
局域网地址列出来（已过滤掉 Clash TUN 的 fake-ip、link-local 这些连不上的）。

⚠ **这个服务没有任何登录验证。** 能连上这个地址的人都能看你的收藏夹、观看历史，
还能下载漫画。只在家里内网用，**千万不要映射到公网**。

**对站点的负担（这是本项目的首要约束）**

这个项目刻意把自己压得比正常浏览网页还轻。核心是一道**全进程限速闸门**：
所有对禁漫的请求都必须经过 `_throttle()`，它保证两次请求之间至少间隔
`JMREADER_MIN_REQUEST_INTERVAL`（默认 0.2 秒 → 最多 5 请求/秒）。
无论开多少线程、多少个来源并发抓取，**都不可能突破这个上限**。

在此之上，能缓存的一律缓存，绝不为同一个东西回源两次：

| 数据 | 缓存位置 | 时长 | 效果 |
|---|---|---|---|
| 随机池 | 内存 **+ 落盘** | 6 小时 | 重启也不重抓 |
| 分类树 / 标签表 | 内存 | 6 小时 | 来回进出「发现」「标签」页 0 请求 |
| 本子详情 | 内存 | 30 分钟 | 反复进出详情页 0 请求 |
| 排行榜 / 搜索 / 收藏夹 | 内存 | 30 分钟 | 翻回上一页 0 请求 |
| 多标签筛选结果 | 内存 | 1 小时 | 同一组合重复筛 0 请求 |
| 章节页图 / 封面 | **磁盘** | 永久（有数量上限） | 同一张图全站只取一次 |

实测（`/api/health` 里的 `upstream` 字段会实时给出这些数字）：

```
首次 /api/home（建池子，7 个来源）        7 次
/api/home × 30（池子已缓存）              0 次
重启进程后首次 /api/home（从磁盘恢复）      0 次
首次多标签筛选（2 标签 × 3 页）            6 次
同一筛选组合 × 10                          0 次
同一关键词搜索 × 5                         1 次
同一封面 × 15                              0 次
```

`GET /api/health` 会返回 `upstream_requests` / `requests_per_hour`，
你可以随时自己核对这个项目到底给站点添了多少负担。

**数据库与存储（踩坑记录：WAL 与 NAS）**

本地库索引、观看历史、登录凭据都存在 `data/jmreader.db` 这一个 SQLite 文件里。
SQLite 默认想用 **WAL（预写式日志）** 模式，但它有个硬性前提：

> **WAL does not work over a network filesystem.**
> All processes using a database must be on the same host computer.
> —— sqlite.org/wal.html

WAL 依赖 `-shm` 文件上的**共享内存**和可靠的文件锁来协调读写。网络共享
（SMB/CIFS、NFS）、部分 NAS 的"资源库"卷、部分容器 volume 上，这套机制会
**静默失效**：写入确实进了 `-wal`，但读连接一直停在旧快照上。

我们在一台 WinNAS 上实测到过完整的事故链：

1. 扫描报告 `added=5`，列表却永远只显示 2 部，`GET /api/library` 连打 20 次都不变
2. 把数据库拉下来直接查，同一张表、同一条连接，前后两条语句结果不同：
   `ORDER BY downloaded_at DESC` 得到 2 行，全表扫描得到 5 行
3. `PRAGMA integrity_check` 给出答案 —— **索引与表不同步**：
   `wrong # of entries in index idx_dl_album_time`

**数据一条没丢，坏的是索引**，而走索引的查询不会报错、只是少返回行。
所以现在启动时会做两件事：

- **日志模式自检**：写完一行立刻读回来。读得到才用 WAL，读不到就自动退回
  不依赖共享内存的 **rollback journal**（`journal_mode=DELETE`）。数据目录在
  本地盘时仍然用 WAL，不会有性能损失。
- **完整性自检**：`PRAGMA quick_check` 发现索引损坏就自动 `REINDEX` 修回来。

两者都会出现在 `GET /api/health` 的 `storage` 段里：

```json
"storage": {
  "db_path": ".../data/jmreader.db",
  "download_dir": ".../data/downloads",
  "journal_mode": "WAL",
  "repair_notes": []
}
```

`journal_mode` 显示 `DELETE` 不是故障，是自检发现这块盘撑不住 WAL 后**按预期降级**；
`repair_notes` 非空说明数据库曾经坏过、已被自动修复。真出问题时可以临时用
`JMREADER_SQLITE_JOURNAL=wal|delete` 强制指定模式来排查。

> ⚠️ 由此引申出一条操作守则：**不要用另一台电脑通过网络去读写正在被使用的
> `jmreader.db`**。需要查看就先把文件复制出来看副本 —— 这正是上面那条
> "all processes must be on the same host" 的意思。

**为什么"随机 10 部"要自己造池子？**
禁漫的 `/random_recommend` 只看名字像随机，实测它**固定返回 30 条，而且短时间内
多次调用结果完全一样** —— 是服务端的一份静态缓存列表，本身不随机。
如果只从这 30 条里抽 10 部，那你无论刷新多少次，**总共也只会见到这 30 部**。

所以池子是合并出来的：`/random_recommend`(30) + `/latest`(80) +
若干个「随机分类 × 随机排序 × 随机页码」的 `/categories/filter`(各 80)。
默认抓 5 个随机页，池子约 **430 部**，缓存 **6 小时并落盘**，
所以一天大约只发 28 次请求，重启也不会重抓。

抓取用 2 个并发线程（限速闸门之下，并发只影响等待时间，不会多打站点）；
单个来源失败会被跳过，不影响整体。
`JMREADER_HOME_POOL_SOURCES=0` 可以退回只用官方推荐位（1 个请求，但池子只有 30 部）。

**导航**
顶栏左侧有一个「返回」按钮，除首页外**每个页面都有**（顶栏是吸顶的，滚动时也在）。
它和浏览器自带后退键共用一套逻辑：站内维护一个访问过的 hash 序列，
能区分"前进到新页面"和"后退"，所以两者不会打架。
如果是直接打开链接或刷新进来的（没有上一页），会退到该页面的上级 ——
比如本地漫画详情退回「本地」列表，其它退到首页。阅读器里的「← 返回」还会
优先回到它所属的漫画详情。

**关于观看历史**
禁漫服务端有 `/watch_list`，但它只告诉你"看过哪些"，**没有页码**，而且必须登录。
所以历史完全本地化（SQLite），记录到页码，这样才能"继续阅读"。

**为什么多标签筛选是本地算的？**
禁漫的搜索接口**只接受一个 tag**（`main_tag=3` + 一个 `search_query`）。
实测拿空格、逗号把多个标签拼起来并不可靠 —— 它返回的集合和单个标签并不相同，
说明那是整串模糊匹配，不是 AND。所以多选只能在本地做集合运算：
每个标签各取若干页，再求交集（同时具备）或并集（任一即可）。

这有代价，所以做了硬性上限：**最多 5 个标签 × 每个标签最多 3 页**，结果缓存 10 分钟。
因此"同时具备"的结果是「在各自前几页范围内同时出现」的近似 ——
对同一套排序规则来说，这等价于取交集后的头部，实用上够用。首次筛选可能要几秒，之后就很快。

**标签怎么搜才准（实测结论）**

*   **面板里那 47 个不是全部标签**。`/categories` 返回的是禁漫挑出来的**常用标签**，
    分成 主題A漫 / 角色·扮演 / 特殊PLAY / 其他 四组。它们和其余标签**属于同一套标签体系** ——
    `search_tag("中文")`、`search_tag("口交")` 和 `search_tag("純愛")` 走的是同一个接口、
    同一个参数（`main_tag=3`），只是没被选进那个面板而已。
    所以筛选框**接受任意标签**，界面上可以直接输入，也可以从漫画详情页点标签带过来。

*   **标签一律以繁体书写**。抽样 20 本、82 个去重标签，含「简体专用字」的为 **0 个**：
    写成 `女僕` / `強制口交` / `吊帶襪` / `過膝襪`，不是 `女仆` / `强制口交` / `吊带袜` / `过膝袜`。

*   **但搜索时多数简体输入也能用**。实测这些简繁写法返回**完全相同的 ID 集合**：

    | 简体 | 繁体 | total |
    |---|---|---|
    | 纯爱 | 純愛 | 10000 |
    | 触手 | 觸手 | 5311 |
    | 调教 | 調教 | 8893 |
    | 护士 | 護士 | 1069 |
    | 眼镜 | 眼鏡 | 8403 |
    | 兽交 | 獸交 | 1303 |
    | 猎奇 | 獵奇 | 3258 |

    **但不是全部如此** —— `女仆` 只有 149 条，`女僕` 有 4223 条，两者结果不同。
    所以「拿不准就用繁体」，最稳妥的办法是**从漫画详情页直接点那个标签**。

*   **瞎编的标签会返回 0 条**，不会退化成模糊匹配（`這絕對不是標籤xyzq` → total=0），
    所以筛选结果不会莫名其妙变多。

*   顺带一提：`/tags`、`/tag`、`/tags/list` 这些接口在禁漫 App API 里**都不存在**，
    没有"拉全量标签"的官方途径。想要全量列表只能靠大量抽样拼，代价太大，故不做。

**排版**
宽屏（≥720px）默认是照搬禁漫网页端的多列网格：竖版封面（2:3），封面左上叠作者、
右上叠分类徽章、右下是收藏标记，封面下面是**标题（最多两行）/ 橙色作者 / 灰色信息行**。
窄屏自动切回列表形态（同样的 DOM，只换 CSS）。顶栏右侧可以手动钉死网格/列表，
以及切换跟随系统/深色/浅色。

**一个必须说明的数据限制**
禁漫的**列表接口不返回单本标签** —— `/search`、`/categories/filter`、`/latest`、
`/favorite` 的每一项都只有 `name / author / category`，`tags` 要么不存在要么是空数组
（`/categories/filter` 顶层那个 `tags` 是**筛选条件**，不是单本标签）。
所以要给每张卡片都显示标签，就得为每一本单独调一次详情接口 —— 一页 80 本，
不可能也不应该这么干。

因此卡片第三行的取值顺序是：**真实标签（本地库里我们自己存的）→ 发布日期**，
两者都没有时留空（收藏夹接口不给日期，所以收藏页的卡片只有两行）。
如果你希望首页那 10 张卡片也带上真实标签，可以在 `/api/home` 里做一次小规模并发补全 ——
10 次请求，有缓存，成本可控，说一声我就加。

## 常见问题

**双击 `run.bat`，窗口一闪就没了**

先别怀疑 Python。按顺序查：

1. **这个项目是怎么到这台机器上的？** 如果是拷贝、解压、robocopy —— **几乎肯定是行尾问题**。
   `.bat` 必须是 CRLF，转换由 git 在检出时完成，拷贝过去的文件不会被转换。
   解决办法：删掉目录，重新 `git clone`。
2. **确认 `.bat` 的行尾**。在项目目录里执行：

   ```bat
   findstr /C:"@echo off" run.bat >nul && echo 文件存在
   ```

   更直接的办法是用记事本打开 `run.bat` 另存为 —— 如果它提示你"换行符会被转换"，
   那就是 LF。
3. **在命令行里手动跑一次**，这样报错不会随窗口消失：

   ```bat
   cd /d 你的项目目录
   run.bat
   ```

   现在的 `run.bat` 在出错时会**主动 pause**，正常情况下你能看到具体原因。

**提示 `Method Not Allowed` 或页面显示了新东西但行为是旧的**

**后端没有重启。** 改文件对已经跑起来的进程没有任何影响。
`/api/health` 会告诉你真相：

```json
"build": { "running": "…", "on_disk": "…", "stale": true }
```

`stale: true` 就是"磁盘上是新代码，进程里还是旧的"。把程序彻底关掉再启动。
