# JMReader

禁漫天堂（JMComic / 18comic）第三方阅读器。**只做漫画**，没有广告、没有小说、没有视频。

前后端分离：后端 FastAPI + SQLite，前端零依赖的静态页面（无框架、无构建步骤）。

## 特性

| 功能 | 说明 |
|---|---|
| **默认页随机** | 打开就是随机 10 部漫画，点「换一批」重掷；池子约 550 部，不是固定那几部 |
| **JM 号定位（车牌号）** | 搜索框里直接输数字就是车牌号，精确定位到那一部，命中即出卡片 |
| **关键词搜索** | 站内 / 作品 / 作者 / 人物，支持排序（最新·观看·图片·爱心·评分·评论）与时间范围 |
| **标签搜索** | 走禁漫原生的 `main_tag=3`，不是拿标签当关键词凑 |
| **标签筛选（多选）** | 内置标签点一下就选中，可多选；支持「同时具备」与「任一即可」两种模式 |
| **分类与排行** | 分类树、标签云、日/周/月/总排行 |
| **收藏夹** | 登录后读取你自己的禁漫收藏夹（含收藏夹分组） |
| **观看历史** | 存在本地，记录到**章节 + 页码**，可以「继续阅读」 |
| **在线阅读** | 长图（下拉）/ 翻页两种模式，阅读进度自动记录 |
| **下载到本地** | 一章一个 ZIP，零重编码零画质损失；可浏览、可阅读、可删除 |
| **本地库** | 「本地」页浏览已下载的漫画，直接读 ZIP 里的图 |
| **排版照搬禁漫网页端** | 宽屏是竖版封面多列网格，封面叠作者/分类徽章，下方标题 + 橙色作者 + 灰色信息行；窄屏自动切列表 |
| **深浅色主题** | 跟随系统 / 深色 / 浅色，随手切换 |
| **无广告** | 用的是禁漫的移动端接口，从头到尾不请求任何广告字段 |

## 快速开始

> 需要 **Python 3.10 或更高版本**（推荐 3.12+）。

依赖**全部装在项目目录内的 `.venv` 里**，不会污染你的全局 Python 环境。

### Windows

```bat
git clone <你的仓库地址> JMReader
cd JMReader
run.bat
```

### macOS / Linux

```bash
git clone <你的仓库地址> JMReader
cd JMReader
chmod +x run.sh
./run.sh
```

看到下面这行就说明起来了，浏览器打开即可：

```
JMReader 正在启动 …
打开浏览器访问： http://127.0.0.1:8756
```

### 手动安装（等价于上面的脚本）

```bash
# 1. 在项目目录内创建虚拟环境
python -m venv .venv

# 2. 激活它
.venv\Scripts\activate        # Windows
source .venv/bin/activate     # macOS / Linux

# 3. 只往这个 venv 里装依赖
pip install -r requirements.txt

# 4. 启动
python -m app
```

> ⚠️ 请不要用 `pip install --user` 或全局 `pip install`。这个项目所有依赖都应当只存在于 `.venv/`。

## 配置

复制 `.env.example` 为 `.env` 再改。所有项都可留空。

| 变量 | 默认 | 说明 |
|---|---|---|
| `JMREADER_HOST` | `127.0.0.1` | 想让局域网手机访问就改成 `0.0.0.0` |
| `JMREADER_PORT` | `8756` | 端口 |
| `JMREADER_DATA_DIR` | `./data` | 数据目录（Cookie、数据库、下载内容） |
| `JMREADER_PROXY` | 空 | 留空 = 自动探测系统代理 |
| `JMREADER_DOWNLOAD_CONCURRENCY` | `1` | 同时下载的任务数，**建议保持 1** |
| `JMREADER_DOWNLOAD_INTERVAL` | `1.2` | 每张图之间的间隔（秒） |
| `JMREADER_HOME_RANDOM_COUNT` | `10` | 默认页随机几部 |
| `JMREADER_HOME_POOL_SOURCES` | `5` | 随机池额外抓几个「随机分类 × 随机页」，设 0 就只用官方推荐位 |
| `JMREADER_HOME_POOL_MAX_PAGE` | `30` | 随机页的页码上限 |
| `JMREADER_MIN_REQUEST_INTERVAL` | `0.2` | **全局限速**：两次上游请求的最小间隔（秒），0 表示不限 |
| `JMREADER_CATEGORIES_TTL` | `21600` | 分类树缓存（秒） |
| `JMREADER_ALBUM_TTL` | `1800` | 详情/搜索/排行缓存（秒） |

## 几个设计决定（以及为什么）

**为什么后端用 Python？**
整套生态都在 Python：[jmcomic](https://github.com/hect0x7/JMComic-Crawler-Python)（MIT，7k+ star）
已经处理好了最麻烦的部分 —— 移动端接口的加解密、**Cloudflare 绕过、域名失效自动切换与重试**。
实测启动时它会自己从域名服务器拉到最新域名，并把 `APP_VERSION` 从 2.1.7 自动升到 2.1.8。
这些才是这类项目真正的死因，而不是"少个接口"。

**为什么图片必须由后端代理？**
实测图床域名的 **TLS 证书校验会失败**，而且域名在轮换（`cdn-msp*.jmapiproxy*.cc` /
`*.jmapinodeudzn.net`），还会挑 Referer。浏览器直连必然挂。
所以封面和章节图全部走 `/api/cover/*` 和 `/api/page/*`，由后端解扰 + 转发 + 本地缓存。

**为什么下载用 ZIP？**
- **零重编码、零画质损失**：图片原样装进 ZIP（`ZIP_STORED`）。实测 13 张图共 2,886,798 字节，
  ZIP 内 `compressed == original`，容器开销只有几百字节。
- **随机访问最快**：读第 37 页只解压那一页。
- **反面对照**：同样的 webp 转成 PDF 会膨胀到 **4～10 倍**（PDF 标准不支持 webp，
  `img2pdf` 只能解码成裸像素再用 zlib 压回去；换成 JPEG 则是有损）。
- **长图不适合当存储格式**：一张超长图的解码内存峰值可达上百 MB，
  而且浏览器对单图尺寸有上限（约 16384px）。所以"长图"我们做成**前端阅读模式**
  （把多页放在一条垂直流里上下排列），观感一样，零 CPU 零重编码。

**为什么只有 1 个下载任务？**
禁漫站点运营不易。这个项目在下载上刻意保持克制：同时只跑一个任务、页与页之间留间隔、
失败才退避重试。**请不要为了"快"去调大 `JMREADER_DOWNLOAD_CONCURRENCY`** ——
真的没必要，也不体面。

**代理怎么配（这是最容易卡住的一步）**

直接连禁漫是**不稳定**的：本机实测连续 5 次只有 2 次能通，其余是
`CertificateVerifyError`（证书校验不过）或连接被重置。挂上本地代理后每次都稳定。

所以推荐挂代理，但**不需要改文件** —— 打开 App 的「设置」页面 →「网络代理」：

| 模式 | 含义 |
|---|---|
| 跟随系统 / 配置文件 | 默认。优先用 `JMREADER_PROXY`，没设就让 jmcomic 探测系统代理 |
| 不使用代理（直连） | 强制直连，连系统代理都不看。一般只用来排查问题 |
| 手动指定代理 | 填 `http://127.0.0.1:7890` 这类地址，比如 Clash / v2rayN |

页面里还有「测试连接」，会真的连一次禁漫并回报成功/失败、耗时、以及失败原因。
设置存在本地数据库里，**优先级高于 `.env`**，所以每台机器都能自己配。

常见端口：Clash `7890`、v2rayN `10809`、Fiddler `8888`。
另外 jmcomic 还认识 `clash` / `v2ray` / `fiddler` / `system` 这几个简写。

**对站点的负担（这是本项目的首要约束）**

这个项目刻意把自己压得比正常浏览网页还轻。核心是一道**全进程限速闸门**：
所有对禁漫的请求都必须经过 `_throttle()`，它保证两次请求之间至少间隔
`JMREADER_MIN_REQUEST_INTERVAL`（默认 0.2 秒 → 最多 5 请求/秒）。
无论开多少线程、多少个来源并发抓取，**都不可能突破这个上限**。

在此之上，能缓存的一律缓存，绝不为同一个东西回源两次：

| 数据 | 缓存位置 | 时长 | 效果 |
|---|---|---|---|
| 随机池 | 内存 **+ 落盘** | 6 小时 | 重启也不重抓 |
| 分类树 / 标签表 | 内存 | 6 小时 | 来回进出「发现」「标签」页 0 请求 |
| 本子详情 | 内存 | 30 分钟 | 反复进出详情页 0 请求 |
| 排行榜 / 搜索 / 收藏夹 | 内存 | 30 分钟 | 翻回上一页 0 请求 |
| 多标签筛选结果 | 内存 | 1 小时 | 同一组合重复筛 0 请求 |
| 章节页图 / 封面 | **磁盘** | 永久（有数量上限） | 同一张图全站只取一次 |

实测（`/api/health` 里的 `upstream` 字段会实时给出这些数字）：

```
首次 /api/home（建池子，7 个来源）        7 次
/api/home × 30（池子已缓存）              0 次
重启进程后首次 /api/home（从磁盘恢复）      0 次
首次多标签筛选（2 标签 × 3 页）            6 次
同一筛选组合 × 10                          0 次
同一关键词搜索 × 5                         1 次
同一封面 × 15                              0 次
```

`GET /api/health` 会返回 `upstream_requests` / `requests_per_hour`，
你可以随时自己核对这个项目到底给站点添了多少负担。

**为什么"随机 10 部"要自己造池子？**
禁漫的 `/random_recommend` 只看名字像随机，实测它**固定返回 30 条，而且短时间内
多次调用结果完全一样** —— 是服务端的一份静态缓存列表，本身不随机。
如果只从这 30 条里抽 10 部，那你无论刷新多少次，**总共也只会见到这 30 部**。

所以池子是合并出来的：`/random_recommend`(30) + `/latest`(80) +
若干个「随机分类 × 随机排序 × 随机页码」的 `/categories/filter`(各 80)。
默认抓 5 个随机页，池子约 **430 部**，缓存 **6 小时并落盘**，
所以一天大约只发 28 次请求，重启也不会重抓。

抓取用 2 个并发线程（限速闸门之下，并发只影响等待时间，不会多打站点）；
单个来源失败会被跳过，不影响整体。
`JMREADER_HOME_POOL_SOURCES=0` 可以退回只用官方推荐位（1 个请求，但池子只有 30 部）。

**导航**
顶栏左侧有一个「返回」按钮，除首页外**每个页面都有**（顶栏是吸顶的，滚动时也在）。
它和浏览器自带后退键共用一套逻辑：站内维护一个访问过的 hash 序列，
能区分"前进到新页面"和"后退"，所以两者不会打架。
如果是直接打开链接或刷新进来的（没有上一页），会退到该页面的上级 ——
比如本地漫画详情退回「本地」列表，其它退到首页。阅读器里的「← 返回」还会
优先回到它所属的漫画详情。

**关于观看历史**
禁漫服务端有 `/watch_list`，但它只告诉你"看过哪些"，**没有页码**，而且必须登录。
所以历史完全本地化（SQLite），记录到页码，这样才能"继续阅读"。

**为什么多标签筛选是本地算的？**
禁漫的搜索接口**只接受一个 tag**（`main_tag=3` + 一个 `search_query`）。
实测拿空格、逗号把多个标签拼起来并不可靠 —— 它返回的集合和单个标签并不相同，
说明那是整串模糊匹配，不是 AND。所以多选只能在本地做集合运算：
每个标签各取若干页，再求交集（同时具备）或并集（任一即可）。

这有代价，所以做了硬性上限：**最多 5 个标签 × 每个标签最多 3 页**，结果缓存 10 分钟。
因此"同时具备"的结果是「在各自前几页范围内同时出现」的近似 ——
对同一套排序规则来说，这等价于取交集后的头部，实用上够用。首次筛选可能要几秒，之后就很快。

**标签怎么搜才准（实测结论）**

*   **面板里那 47 个不是全部标签**。`/categories` 返回的是禁漫挑出来的**常用标签**，
    分成 主題A漫 / 角色·扮演 / 特殊PLAY / 其他 四组。它们和其余标签**属于同一套标签体系** ——
    `search_tag("中文")`、`search_tag("口交")` 和 `search_tag("純愛")` 走的是同一个接口、
    同一个参数（`main_tag=3`），只是没被选进那个面板而已。
    所以筛选框**接受任意标签**，界面上可以直接输入，也可以从漫画详情页点标签带过来。

*   **标签一律以繁体书写**。抽样 20 本、82 个去重标签，含「简体专用字」的为 **0 个**：
    写成 `女僕` / `強制口交` / `吊帶襪` / `過膝襪`，不是 `女仆` / `强制口交` / `吊带袜` / `过膝袜`。

*   **但搜索时多数简体输入也能用**。实测这些简繁写法返回**完全相同的 ID 集合**：

    | 简体 | 繁体 | total |
    |---|---|---|
    | 纯爱 | 純愛 | 10000 |
    | 触手 | 觸手 | 5311 |
    | 调教 | 調教 | 8893 |
    | 护士 | 護士 | 1069 |
    | 眼镜 | 眼鏡 | 8403 |
    | 兽交 | 獸交 | 1303 |
    | 猎奇 | 獵奇 | 3258 |

    **但不是全部如此** —— `女仆` 只有 149 条，`女僕` 有 4223 条，两者结果不同。
    所以「拿不准就用繁体」，最稳妥的办法是**从漫画详情页直接点那个标签**。

*   **瞎编的标签会返回 0 条**，不会退化成模糊匹配（`這絕對不是標籤xyzq` → total=0），
    所以筛选结果不会莫名其妙变多。

*   顺带一提：`/tags`、`/tag`、`/tags/list` 这些接口在禁漫 App API 里**都不存在**，
    没有"拉全量标签"的官方途径。想要全量列表只能靠大量抽样拼，代价太大，故不做。

**排版**
宽屏（≥720px）默认是照搬禁漫网页端的多列网格：竖版封面（2:3），封面左上叠作者、
右上叠分类徽章、右下是收藏标记，封面下面是**标题（最多两行）/ 橙色作者 / 灰色信息行**。
窄屏自动切回列表形态（同样的 DOM，只换 CSS）。顶栏右侧可以手动钉死网格/列表，
以及切换跟随系统/深色/浅色。

**一个必须说明的数据限制**
禁漫的**列表接口不返回单本标签** —— `/search`、`/categories/filter`、`/latest`、
`/favorite` 的每一项都只有 `name / author / category`，`tags` 要么不存在要么是空数组
（`/categories/filter` 顶层那个 `tags` 是**筛选条件**，不是单本标签）。
所以要给每张卡片都显示标签，就得为每一本单独调一次详情接口 —— 一页 80 本，
不可能也不应该这么干。

因此卡片第三行的取值顺序是：**真实标签（本地库里我们自己存的）→ 发布日期**，
两者都没有时留空（收藏夹接口不给日期，所以收藏页的卡片只有两行）。
如果你希望首页那 10 张卡片也带上真实标签，可以在 `/api/home` 里做一次小规模并发补全 ——
10 次请求，有缓存，成本可控，说一声我就加。
